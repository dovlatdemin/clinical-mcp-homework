# Шпаргалка к защите: контрольные вопросы

Ответы привязаны к коду этого репозитория — на защите можно показать каждый
тезис вживую.

---

## 1. Чем MCP отличается от классических REST API и OpenAPI при работе с ИИ-агентами?

**REST/OpenAPI** описывает *адреса и HTTP-глаголы*: статическая спецификация,
клиент пишется вручную под каждый сервис, связка N агентов × M сервисов
превращается в N×M интеграций.

**MCP** описывает *возможности инструментов* для модели:

- **Динамическое обнаружение**: клиент в рантайме вызывает `tools/list` и
  получает имена, человекочитаемые описания и JSON-схемы параметров.
  Наша форма в `app.py` строится из этих схем автоматически — ни одно поле
  не захардкожено под конкретный сервер.
- **Семантика для LLM**: описания параметров (`Field(description=...)`) читает
  модель и сама решает, какой инструмент вызвать и с какими аргументами.
  OpenAPI такого канала «документация → рассуждение модели» не даёт.
- **Единый протокол**: JSON-RPC 2.0, одинаковый жизненный цикл
  (`initialize` → работа → shutdown) и формат ошибок для любого сервера;
  транспорт (stdio / SSE / Streamable HTTP) отделён от набора инструментов.
  У нас три разных сервера — и роутер `clients/router.py` работает с ними
  через один интерфейс.

## 2. Почему в stdio запрещён print()? Куда направлять логи?

Транспорт stdio — анонимные каналы ОС: **stdout сервера является входным
потоком JSON-RPC клиента**. Любой `print()` вставляет в поток не-JSON байты,
и парсер клиента падает.

Живой пример из нашей практики: внешний сервер medical-mcp печатает баннер
`✅ Medical MCP Server running on stdio` в stdout — клиент SDK ответил
`ValidationError: Invalid JSON` именно на эту строку.

Правильно: логи — **строго в stderr** (или в файл). В нашем
`servers/stdio_server.py`:

```python
logging.basicConfig(stream=sys.stderr, level=logging.INFO, ...)
```

Проверка чистоты протокола: `python -m clients.stdio_client 2>stderr.log` —
в stdout только JSON-RPC, весь журнал в stderr.log.

## 3. Структура JSON-RPC 2.0 для initialize и tools/call

Общие поля: `jsonrpc: "2.0"` — версия протокола; `id` — коррелятор
запроса и ответа; `method`, `params`. **Уведомления (notifications) id не имеют.**

**Инициализация** (запрос → ответ → уведомление):

```json
{"jsonrpc": "2.0", "id": 1, "method": "initialize",
 "params": {"protocolVersion": "2024-11-05",
            "capabilities": {"tools": {}},
            "clientInfo": {"name": "clinical-ui", "version": "1.0"}}}

{"jsonrpc": "2.0", "id": 1,
 "result": {"protocolVersion": "2024-11-05",
            "capabilities": {"tools": {"listChanged": false}},
            "serverInfo": {"name": "rehab-scales", "version": "1.x"}}}

{"jsonrpc": "2.0", "method": "notifications/initialized"}
```

**Вызов инструмента** (запрос → ответ / ошибка):

```json
{"jsonrpc": "2.0", "id": 2, "method": "tools/call",
 "params": {"name": "body_mass_index",
            "arguments": {"weight_kg": 74.5, "height_cm": 175}}}

{"jsonrpc": "2.0", "id": 2,
 "result": {"content": [{"type": "text", "text": "{...}"}], "isError": false}}

{"jsonrpc": "2.0", "id": 2,
 "error": {"code": -32602, "message": "Invalid params"}}
```

Показать на защите: инспектор внизу страницы приложения отображает именно
эти пакеты после каждого расчёта.

## 4. SSE vs stdio при масштабировании на команду врачей

| Критерий | stdio | SSE / Streamable HTTP |
|---|---|---|
| Модель | 1 клиент = 1 дочерний процесс на той же машине | Один демон обслуживает много клиентов |
| Изоляция | Падение процесса не трогает хост и других врачей | Отказ демона бьёт по всем — нужны мониторинг и ретраи |
| Безопасность | Нет сети — чувствительные данные не покидают машину | За пределами localhost нужны TLS и аутентификация |
| Эксплуатация | Нулевая конфигурация, жизненный цикл у клиента | Сетевые таймауты, пулы повторных попыток, обновление демона |
| Обновление шкал | У каждого своя копия | Централизованно, один раз для всей команды |

**Вывод для команды врачей**: SSE/HTTP выигрывает — один сервер отделения с
актуальными калькуляторами обслуживает всех (наш `:8000`); stdio остаётся
лучшим для персональных закрытых расчётов и чувствительных данных, потому
что не открывает сетевой поверхности вообще.

## 5. Как защитить медицинский калькулятор от галлюцинаций LLM при автоматической передаче параметров из истории болезни?

Слоёная защита (всё реализовано в проекте):

1. **Считает код, а не модель.** LLM только выбирает инструмент и заполняет
   параметры; балл вычисляет детерминированный Python. Галлюцинировать
   «результат формулы» модель физически не может.
2. **Строгая типизация**: JSON Schema + Pydantic, `Literal` для пола, enum
   для категорий. Модель не передаст «примерно 70» или «муж».
3. **Серверная валидация границ**: физиологические диапазоны в
   `servers/sse_server.py` (`PHYSIO_LIMITS`); выход за границы — `warnings`,
   а не тихий абсурдный результат.
4. **Перекрёстные проверки согласованности**: «симптомов нет, но указана
   зависимость от помощи» → `ValueError` → `ToolError` (`servers/stdio_server.py`).
5. **Мета-инструмент `list_calculators`**: модель перед вызовом читает
   допустимые диапазоны и единицы измерения — меньше шансов перепутать
   мкмоль/л с мг/дл.
6. **Sanitizer с прозрачными заметками**: все авто-подстановки (Smart Defaults)
   возвращаются списком и показываются врачу — ничего не меняется молча.
7. **Человек в контуре**: результат предварительный, утверждает врач;
   инспектор JSON-RPC позволяет аудировать, что именно ушло в расчёт;
   к каждой шкале приложен первоисточник (DOI / приказ № 788н).
8. **Минимизация данных**: в параметры — только структурированные поля,
   свободный текст истории болезни и идентификаторы в инструмент не идут.
